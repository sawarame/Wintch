# Wintch 憲章

macOS 向けウィンドウ単位スイッチャー＆ランチャー「Wintch」の設計・実装における最上位の原則、アーキテクチャ制約、および品質基準を定義する。

## Core Principles

### 1. 最小権限およびオプトインの原則（Privacy by Design）
基本体験である「リスト型スイッチャー」「アイコン型スイッチャー」および「リスト型検索ランチャー」は、アクセシビリティ権限（`AXUIElement`）およびウィンドウメタデータのみで完結させなければならず、画面収録権限を一切要求・使用してはならない（MUST NOT）。
ウィンドウのキャプチャ表示機能（通常スイッチャーの Windows Alt+Tab 風カードグリッドおよび検索ランチャーのサムネイル付きリスト表示）に限り、ユーザーが設定またはメニューバーで「キャプチャ表示型」を明示的に選択した場合のみ、オプトインで画面収録権限（`ScreenCaptureKit` 等の Apple 標準フレームワーク）を使用してよい。

- **制約**:
  - 通常スイッチャーおよび検索ランチャーの双方で「キャプチャ表示型」が選択されていない間（「リスト型」または「アイコン型」のみ）は、画面収録権限の許可ダイアログ誘導や画面キャプチャ処理を一切実行してはならない（MUST NOT）。
  - キャプチャ画像はスイッチャー／ランチャー上の視覚的識別のためメモリ上の一時保持・描画に限定し、ディスクへの永続保存や外部ネットワーク送信を行ってはならない（MUST NOT）。
- **根拠**: プライバシーを重視するユーザーには画面収録権限ゼロの運用を保証しつつ、ビジュアル識別を望むユーザーにはオプトインでキャプチャ表示を提供するため。

### 2. 過剰機能の排除（シンプルさの徹底）
AltTab のような多機能化・高機能化は目指さない。設定項目や UI 要素は「目的のウィンドウを素早く特定し切り替える（および検索ランチャーから未起動アプリを起動する）」というコア体験に必要な最小限にとどめなければならない（MUST）。表示形式の切り替え（「リスト型」／「アイコン型」／「キャプチャ表示型」）など最小限の選択肢のみを許容し、細かな装飾設定や過剰なカスタマイズ項目は増やさない。

- **根拠**: ユーザーの認知負荷を最小化し、日常的な操作における迷いをなくすとともに、コードベースの保守性を高く維持するため。

### 3. 起動と応答の高速性（ゼロレイテンシ）
常駐時の CPU・メモリ消費を極限まで抑え、ショートカット入力から UI 表示、ウィンドウ切り替え完了まで体感遅延ゼロ（即時応答）のレスポンシブな動作を維持しなければならない（MUST）。キャプチャ取得等の比較的重い処理を行う場合でも、パネルの即時表示を妨げてはならず（MUST NOT）、非同期更新および適切なキャッシュ上限管理によりメモリ肥大と応答遅延を防止しなければならない（MUST）。

- **根拠**: ウィンドウ切り替えは 1 日に数十回〜数百回行われる超高頻度アクションであり、わずかな遅延も作業フローと集中力を阻害するため。

### 4. 依存関係の最小化（外部ライブラリ依存ゼロ）
外部サードパーティ製ライブラリ（Swift Package Manager 等）の追加は原則禁止とし、Apple 標準フレームワークのみで実装しなければならない（MUST）。

- **根拠**: 外部依存によるサプライチェーンリスクの排除、長期的なメンテナンス性の確保、およびビルド速度・バイナリサイズの最適化を実現するため。

### 5. 非公開 API の禁止と安全なフォールバック
Apple の審査でリジェクト対象となる非公開 API（`CGS*` 系のプライベート関数など）は一切使用してはならない（MUST NOT）。また、アクセシビリティ権限が未許可の状態でもアプリがクラッシュしてはならず、ユーザーに対して権限許可の手順とシステム設定への誘導画面を適切に表示しなければならない（MUST）。さらに、キャプチャ表示型が選択された状態で画面収録権限が未許可・拒否されている場合や、最小化・別操作スペース等によりキャプチャが取得できない場合でもクラッシュしてはならず、アプリアイコン等のプレースホルダー表示と権限案内により安全にウィンドウ切り替えを継続できなければならない（MUST）。

- **根拠**: Mac App Store での公開可能性と Homebrew 配布の両立を担保し、初回起動時や権限未許可環境でも安全かつ親切にユーザーを支援するため。

## 技術スタックおよびアーキテクチャ制約

### ターゲット環境および開発言語
- **対象 OS**: macOS 14.0 (Sonoma) 以降を対象とし、最新の Swift 言語機能および API を活用する。
- **言語**: Swift 6.0 を使用する。

### UI フレームワーク
- 設定画面やウィンドウリスト表示などの UI は SwiftUI で構築する。
- 最前面フローティングパネルの挙動制御（`NSPanel`）や IME 優先検索フィールド（`NSTextField`）、グローバルイベント監視など、SwiftUI のみでは実現困難な必要最小限の範囲に限り AppKit / Carbon 等の標準 API を使用する。

### アーキテクチャ（MVVM + Services）
- **状態管理**: 状態管理には Swift 標準の `@Observable` マクロおよび `@MainActor` を使用する。レガシーな `ObservableObject` や `@Published` は使用してはならない（MUST NOT）。
- **低レイヤー API の隔離**: macOS の低レイヤー API（`CGWindowListCopyWindowInfo`、`AXUIElement`、`CGEventTap`、`RegisterEventHotKey`、`ScreenCaptureKit` 等）はすべて `Services/` 層に隔離・カプセル化し、`Views/` や `ViewModels/` から直接呼び出してはならない（MUST NOT）。

## コーディング規約・品質基準および配布方針

### コードの可読性と明快さ
- 過度な抽象化、複雑な独自ジェネリクス、自作マクロの使用は避け、標準的で明快な Swift コードを記述しなければならない（MUST）。
- すべてのクラス、構造体、列挙型、関数、メソッドには SwiftDoc 形式（`///`）で日本語のドキュメントコメントを記述し、インラインコメントも日本語で記述する。

### テスト可能性（Testability）
- ウィンドウ一覧のフィルタリング（ノイズ・ゴーストウィンドウ除外）、ソート、ファジー検索、選択位置計算、グリッドレイアウト、ショートカット競合検証などの純粋なビジネスロジックは、`Domain/` に切り出してユニットテスト（Swift Testing）が可能な構造に設計しなければならない（MUST）。

### ライセンスと配布
- すべてのソースコードは MIT License のもとで公開・管理される前提で記述する。
- Developer ID 署名・Apple 公証済みの GitHub Releases 配布および Homebrew Cask 配布（`sawarame/tap/wintch`）の品質を維持する。

## Governance

本憲章は、Wintch プロジェクトにおける最上位の開発方針であり、すべての設計判断・コード変更・仕様変更に優先する。

- すべての設計・実装・コードレビューにおいて本憲章への準拠を検証しなければならない（MUST）。
- オプトイン条件を満たさない画面収録権限の使用（リスト型・アイコン型での使用）、キャプチャ画像のディスク保存・外部送信、サードパーティ製ライブラリの導入、非公開 API の使用、低レイヤー API の `Services/` 外への漏洩など、本憲章に違反する変更は原則として承認されない。
