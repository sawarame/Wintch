# 機能仕様書: ランチャーおよびリスト型スイッチャーの選択候補スクロール追従修正

**Feature Branch**: `018-fix-launcher-scroll`

**Created**: 2026-11-17

**Status**: Draft

**Related Issue**: [#25](https://github.com/sawarame/Wintch/issues/25)

**Input**: User description: "ランチャーを起動し、起動しているウィンドウや候補アプリが表示しきれずスクロールバーが表示されるが、方向キーで候補を移動してもスクロールされず、どの候補を選択したかわからない状態になってしまう。候補を選択したら、それに合わせてスクロールも移動するようにしてほしい。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 検索ランチャーで選択候補の移動に合わせてリストが自動スクロールする (Priority: P1)

ユーザーは、検索ランチャーを起動した際に多数のウィンドウやアプリ起動候補が表示され、パネルの最大高さを超えてスクロールバーが表示される状態であっても、方向キー（`↓` / `↑`）やショートカットキー（`Option + Tab` 等）で候補を上下に移動すれば、現在選択中の候補が常に画面内の見える位置へ自動でスクロール追従することを期待する。

**Why this priority**: Issue #25 で報告されている通り、スクロールが発生する件数の候補がある状態で方向キーによる移動を行っても表示範囲が移動しないと、ユーザーは今どの候補を選択しているか視認できず、誤ったウィンドウやアプリを開いてしまうため、ランチャー操作の基本体験を損なう最優先課題である。

**Independent Test**: ランチャーモードで最大表示高さを超える件数のウィンドウ候補およびアプリ起動候補を表示した状態から、下方向キーまたは上方向キーで表示領域外の候補へ選択を移動させたとき、リストの表示領域（スクロール位置）が選択候補を視認できる位置へ実際に追従移動することで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 検索ランチャーが開いており、一覧の最大高さを超える件数のウィンドウ候補が存在して縦スクロールバーが表示されている状態, **When** ユーザーが `↓` キー等の選択移動操作を繰り返し、初期表示領域の下端より外側にある候補を選択する, **Then** リストのスクロール位置が自動的に下方へ移動し、現在選択・ハイライトされている候補行が確実に可視領域内に表示される。
2. **Given** 検索ランチャーでウィンドウ候補の下に「アプリを起動」セクション（アプリ起動候補）が続いて表示され、全体として縦スクロールが発生している状態, **When** ユーザーが `↓` キー等でウィンドウ候補セクションからアプリ起動候補セクションへ移動し、さらに下方のアプリ起動候補を選択する, **Then** セクションを跨いでもスクロール位置が途切れることなく追従し、選択中のアプリ起動候補が可視領域内に表示される。
3. **Given** 検索ランチャーで下方へスクロールされた候補を選択している状態, **When** ユーザーが `↑` キー等で上方へ移動して初期表示領域側へ戻る、または先頭・末尾間で循環移動する, **Then** スクロール位置が選択先の候補（上端側・末尾側を含む）を視認できる位置へ即座に追従する。

---

### User Story 2 - 検索絞り込み・再表示・通常リスト型スイッチャーでもスクロール追従と初期位置の整合性を維持する (Priority: P2)

ユーザーは、検索ランチャーでキーワード入力・変更を行った場合や、通常スイッチャー（リスト型）で多数のウィンドウを切り替えている場合でも、選択カーソルの変化とスクロール位置が常に一致し、見失うことなく目的のウィンドウ・アプリを特定できることを期待する。

**Why this priority**: ランチャーと通常スイッチャー（リスト型）は共通のリスト表示構造を利用しており、検索による一覧更新やリスト型スイッチャーでの多ウィンドウ切り替え時にも同様のスクロール不整合を起こさないようにすることで、アプリ全体の一貫した操作性を保証するため。

**Independent Test**: ランチャーで下方スクロール後に検索文字列を更新して先頭選択へ戻した場合、パネルを閉じて再表示した場合、および通常スイッチャー（リスト型）で多数ウィンドウを移動した場合のそれぞれで、選択中の行が可視領域内に位置していることで検証できる。

**Acceptance Scenarios**:

1. **Given** 検索ランチャーで下方の候補までスクロールした状態, **When** ユーザーが検索文字列を入力または変更し、候補一覧が再構築されて選択位置が先頭へ戻る, **Then** 変更後の先頭選択候補が可視領域内に表示されるようスクロール位置も整合する。
2. **Given** 通常スイッチャー（リスト型）が開いており、最大高さを超える件数のウィンドウが存在して縦スクロールバーが表示されている状態, **When** ユーザーがトリガーキー（`Option + Tab` / `Option + Shift + Tab` 等）または矢印キーで表示領域外のウィンドウへ移動する, **Then** 選択中のウィンドウ行が可視領域内に見えるようリストが自動スクロール追従する。
3. **Given** ランチャーで手動（トラックパッド・マウスホイール）またはキーボードによりスクロールさせた後にパネルを閉じ、再度ランチャーを開いた状態, **When** 初期状態の候補一覧が表示される, **Then** 初期選択されている先頭候補が見える位置から表示される。

---

### Edge Cases

- **スクロールバーが不要な少数件数の場合**: 全候補がパネルの最大高さ内に収まっている状態では、方向キー移動時に不要なスクロールやレイアウトのガタつきが発生しないこと。
- **先頭⇔末尾の循環移動（ラップアラウンド）**: インデックス `0` から上移動で末尾へ飛ぶ場合、および末尾から下移動でインデックス `0` へ戻る場合のように表示領域から大きく離れた位置へ一気に選択が移動しても、遅延生成領域を含め確実にスクロール追従すること。
- **ウィンドウ候補とアプリ起動候補の同一名称・多数混在**: ウィンドウ候補の識別子とアプリ起動候補の識別子が類似している場合でも、それぞれが一意に区別され、誤ったセクションや行へスクロールしないこと。
- **候補クローズ後の選択位置補正**: ランチャーまたはリスト型スイッチャー上で選択中のウィンドウを閉じて候補一覧が再構築された際も、補正後の選択候補が可視領域内に収まること。
- **日本語 IME 変換中の操作**: 検索入力欄で IME の未確定文字列がある状態では、上下矢印キーは従来通り IME の変換候補選択として処理され、確定後のリスト候補移動時のみリストスクロールが追従すること。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、検索ランチャーの表示領域高さを超える候補一覧が表示されている状態において、キーボード操作（`↑` / `↓` 方向キー、および通常スイッチャーショートカットによる前後移動）で選択候補が変更された際、選択中の候補行が可視領域内に収まるようリストを自動スクロールさせなければならない（MUST）。
- **FR-002**: システムは、検索ランチャーにおいてウィンドウ候補セクションとアプリ起動候補セクション（「アプリを起動」配下）が連続表示されている場合でも、双方の候補行を区別した一意の識別契約のもとでセクションを跨いだスクロール追従を一貫して機能させなければならない（MUST）。
- **FR-003**: システムは、リストの末尾から先頭へ、または先頭から末尾へ選択が循環移動した場合のように、現在の可視領域外にある遠くの候補へ選択が移った際も、対象候補が可視領域内に表示される位置まで確実にスクロールさせなければならない（MUST）。
- **FR-004**: システムは、検索ランチャーで検索クエリが変更されて選択インデックスが先頭へ戻った場合、ならびにパネルを閉じて再度表示した場合において、初期／再設定された選択候補が可視領域内に見える状態を保証しなければならない（MUST）。
- **FR-005**: システムは、リスト表示構造を共有する通常スイッチャー（リスト型）においても、最大高さを超えるウィンドウ候補が表示されている際の選択移動に合わせて自動スクロール追従を機能させなければならない（MUST）。
- **FR-006**: システムは、リスト内の遅延構築される行やセクション見出しの有無にかかわらず、すべての候補行で選択状態のハイライトとスクロール先の対象行が常に一致していなければならない（MUST）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 表示可能高さを超える候補数（例：ウィンドウ候補 15 件＋アプリ起動候補 15 件など）の検索ランチャー上で、`↓` / `↑` キーによる選択移動を 1 回行うごとに 100% のケースで選択候補行がスクロール可視領域内に収まる。
- **SC-002**: ウィンドウ候補セクションからアプリ起動候補セクションへの横断移動、および先頭⇔末尾の循環移動を行った場合でも、選択行が可視領域外に取り残される事象が 0 件である。
- **SC-003**: 通常スイッチャー（リスト型）で表示高さを超えるウィンドウ一覧を表示した状態からの候補移動においても、100% のケースで選択行が可視領域内へスクロール追従する。
- **SC-004**: 本修正の追加テストおよび既存自動テスト全件がパスし、プロジェクトのビルドがエラーなく完了する。

## Assumptions

- 検索ランチャーおよび通常スイッチャー（リスト型）は既存の単一縦スクロールリスト構造（最大高さ上限あり）を維持し、視覚デザイン（行高さ・角丸・ハイライト配色・セクション見出し）および操作体系（`↑` / `↓`、IME 優先、修飾キー制御）は変更しない。
- スクロール追従の挙動は、既存の設計契約（`specs/006-launcher-app-launch/contracts/launcher-app-launch-contracts.md` 等）で定義されている単一スクロール領域での自動スクロール追従の期待仕様を実際に動作させる修正である。
