# 機能仕様書: キャプチャ表示型スイッチャーにおけるサムネイル消失の防止とキャッシュ整合性改善

**Feature Branch**: `014-fix-capture-disappearing`

**Created**: 2026-11-17

**Status**: Draft

**Related Issue**: [#16](https://github.com/sawarame/Wintch/issues/16)

**Input**: User description: "Fix disappearing window thumbnails in capture switcher after prolonged use and repeated window open/close (Issue #16)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多数のウィンドウを開閉する長時間利用でも既存ウィンドウのキャプチャが消えない (Priority: P1)

ユーザーは、キャプチャ表示型の通常スイッチャーを有効にして長時間作業を続け、作業中に多数のドキュメントやダイアログ・ブラウザウィンドウを開閉した後であっても、現在開いているウィンドウについて一度取得されたキャプチャ画像が消えてアプリアイコン表示に戻ってしまうことなく、スイッチャーを開いた瞬間にそのまま視覚的に判別できることを期待する。

**Why this priority**: Issue #16 で報告された中心的な不具合であり、使っているうちにせっかくのキャプチャプレビューがアイコンに戻ってしまい「再度ウィンドウを開き直さないと戻らない」状態はキャプチャ表示型スイッチャーのコア価値を大きく損なうため。

**Independent Test**: キャプチャ表示型を有効にした状態で多数のウィンドウや一時ダイアログを開閉し、閉じられたウィンドウが破棄された後も開いたまま残っているウィンドウのキャプチャ画像がスイッチャー再表示時に失われず即時表示されること、ならびに直近利用中のウィンドウほど優先的にプレビューが保持されることで検証できる。

**Acceptance Scenarios**:

1. **Given** キャプチャ表示型で複数のウィンドウがすでにキャプチャ済みである状態, **When** ユーザーが通常の操作（閉じるボタンやアプリケーション内の閉じる操作など、スイッチャー外での操作を含む）で別の多数のウィンドウを開閉した後にスイッチャーを起動する, **Then** 閉じられたウィンドウの古いプレビュー情報は整理され、開いたまま残っているウィンドウのキャプチャ画像が追い出されずに即座に表示される。
2. **Given** キャプチャ保持数の上限に近い、または上限を超える多数のウィンドウが開かれている状態, **When** ユーザーが直近アクティブにしていたウィンドウと長期間使っていないウィンドウを含む状態でスイッチャーを開閉・新規キャプチャを行う, **Then** 直近アクティブ順（MRU）で優先度の高いウィンドウのキャプチャ画像ほど保持優先度が高く維持され、直近利用ウィンドウから先に消える逆転現象が発生しない。
3. **Given** 通常の作業範囲で多数のウィンドウを開いている状態（50〜100 枚規模）, **When** キャプチャ表示型スイッチャーを利用し続ける, **Then** 十分な上限（100 件規模）により開いているウィンドウのキャプチャ画像が容易に欠落せず、視覚的なプレビューが維持される。

---

### User Story 2 - ウィンドウの状態・タイトル変化や再照合時にもキャプチャの紐付けが失われない (Priority: P1)

ユーザーは、開いているウィンドウのタイトルが変わったり（Web ページの遷移・タブ切替・ファイル保存等）、リサイズや表示状態の変化が起きたりした後でも、そのウィンドウと既取得キャプチャ画像との対応付けが維持され、スイッチャー上で突如アイコン表示に変わらないことを期待する。

**Why this priority**: 長時間の作業中にはウィンドウのタイトル変化・サイズ変化・状態変化が頻繁に発生するため、キャッシュ自体が存在してもウィンドウ識別と対応付けが揺らぐと同様にキャプチャが消えたように見えるため。

**Independent Test**: 同一アプリ内に複数ウィンドウや補助ウィンドウ・サイズ変化を伴うウィンドウが存在する状態で、タイトル変更・ウィンドウ移動／リサイズ・別スペースへの行き来等を行っても、同一ウィンドウに同一のキャプチャ識別が維持されアイコン表示に劣化しないことで検証できる。

**Acceptance Scenarios**:

1. **Given** 同一アプリに複数ウィンドウ（または不可視の補助ウィンドウ／無名ウィンドウ）が存在し、対象ウィンドウがキャプチャ済みである状態, **When** 対象ウィンドウのタイトルが変化する、またはサイズ・位置が変わった状態でスイッチャーを開く, **Then** 前回紐付いていたウィンドウ識別が正当に生存している限り同一の対応付けが維持され、無名補助ウィンドウ等への誤乗り換えによってプレビューが消失しない。
2. **Given** サイズ変更等により近接座標での照合から包含判定等の補助照合へフォールバックする状態, **When** 当該ウィンドウの対応付けを再評価する, **Then** 前回までの同一ウィンドウ識別との連続性が優先考慮され、同一ウィンドウのプレビュー表示が維持される。

---

### User Story 3 - 再取得が一時的に遅延・失敗する状況でも既存プレビューを維持し最小権限原則を守る (Priority: P2)

ユーザーは、多数のウィンドウが同時に開かれている環境や一部ウィンドウの一時的な再取得失敗・遅延が起きる場面でも、すでに保持していたプレビュー画像が消去されてアイコンに戻ることはなく、またリスト型や検索ランチャー利用時には従来通り画面収録権限やキャプチャ処理が一切動作しないことを期待する。

**Why this priority**: 「使っていて急に消える」体験を防ぐ上でキャッシュ保護と既存オプトイン原則（憲章第1原則）の両立が不可欠であるため。

**Independent Test**: キャプチャ再取得に失敗するウィンドウや別スペース／最小化中のウィンドウが含まれる状態でスイッチャーを起動しても既存の有効プレビューが保持されること、ならびにリスト型・検索ランチャー時にはキャッシュ保持数が 0 件に保たれることで検証できる。

**Acceptance Scenarios**:

1. **Given** 一時的に最新プレビューの取得に失敗またはタイムアウトするウィンドウが存在するが、そのウィンドウの有効な直前プレビューが保持されている状態, **When** スイッチャーを起動して非同期更新を実行する, **Then** 取得失敗によって直前のプレビューが消去されたりアイコンへ戻されたりせず、直前の有効なプレビューが引き続き表示される。
2. **Given** 設定画面で通常スイッチャーの表示形式を「リスト型」へ変更した状態、または検索ランチャーを起動した状態, **When** それぞれのモードを使用する, **Then** メモリ上のキャプチャプレビューは即座に全破棄され（リスト型切替時）、画面収録権限の確認やキャプチャ処理は一切実行されない。

---

### Edge Cases

- **スイッチャー外で大量に閉じられた直後の起動**: 前回スイッチャー表示から今回の表示までの間に 50 枚以上のウィンドウやダイアログがスイッチャー外で開閉された場合でも、起動時点で既に閉じられているウィンドウ分は整理対象となり、現在開いているウィンドウのプレビュー保持を圧迫しないこと。
- **開いているウィンドウ数が保持上限（100 件）を超える場合**: 上限を超える場合でも直近利用順（MRU）で優先度の低い最古のエントリから破棄され、最上位の直近利用ウィンドウが優先保持されること。
- **非同期キャプチャ実行中に別ウィンドウが閉じられた場合**: 非同期取得の完了待ち中に閉じられたウィンドウの結果が遅れて到着しても、キャッシュや画面状態へ再混入しないこと。
- **ウィンドウが実際に閉じられて再生成された場合**: 同一アプリで旧ウィンドウを閉じて新ウィンドウを開いた場合は別ウィンドウとして扱われ、新ウィンドウの最新プレビューが取得されること。
- **画面収録権限が途中で取り消された場合**: 権限未許可・取り消しを検知した際は従来通り安全にプレースホルダー表示と権限案内バナーへ切り替え、保持していた一時プレビューも即時破棄すること。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、キャプチャ表示型スイッチャーの表示時（または有効ウィンドウ一覧の評価時）に、現在開いている有効なウィンドウ一覧に含まれない閉じ済みウィンドウの一時キャプチャプレビューを自動的に整理・破棄しなければならない（MUST）。
- **FR-002**: システムは、一時キャプチャプレビューのキャッシュにアクセス・格納する際、直近利用順（MRU）の上位ウィンドウほど追い出し優先順位が低く（最新保持側に）なるよう順序を正しく維持しなければならない（MUST）。スイッチャー起動時の初期プレビュー読み込み順序によって直近利用ウィンドウが追い出し対象へ押し出されてはならない（MUST NOT）。
- **FR-003**: システムは、一時キャプチャプレビューのメモリ保持上限を従来の 50 件から 100 件へ引き上げ、多数のウィンドウを併用する通常利用において開いているウィンドウのプレビューが容易に欠落しないようにしなければならない（MUST）。同時に、不要になった閉じ済みウィンドウの即時整理によりメモリ消費を必要最小限に抑制しなければならない（MUST）。
- **FR-004**: システムは、ウィンドウとシステムウィンドウ識別子の再照合において、前回紐付いていた識別子が現在も有効かつ正当な実ウィンドウとして生存している場合に、タイトルの一時変化・無名補助ウィンドウの共存・サイズ変化時の包含照合フォールバックによって誤って別の識別子へ切り替わったり識別子が失われたりしないよう連続性を維持しなければならない（MUST）。
- **FR-005**: システムは、再キャプチャ処理が一時的に失敗・タイムアウトした場合でも、既に有効な直前プレビューが存在するウィンドウについてはプレビューを消去せず保持し続けなければならない（MUST）。
- **FR-006**: システムは、リスト型スイッチャーおよび検索ランチャーにおける画面収録権限不使用・リスト型切替時の即時全キャッシュ破棄・キャプチャ画像のメモリ限定保持（ディスク非保存・外部送信禁止）という既存原則を維持しなければならない（MUST）。

### Key Entities *(include if feature involves data)*

- **WindowCaptureThumbnailCache（一時サムネイルメモリキャッシュ）**: ウィンドウ識別子ごとに最新の縮小プレビュー画像をメモリ内のみで保持し、生存ウィンドウとの同期整理および正しい直近利用順に基づく上限管理（最大 100 件）を行う一時記憶領域。
- **WindowIdentityContinuity（ウィンドウ識別連続性）**: スイッチャーで管理する各ウィンドウ項目とシステム側の描画ウィンドウ識別子との対応付け。状態やタイトルが変化しても正当な識別子が維持されることで、視覚プレビューとの紐付けを途切れさせない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: キャプチャ済みウィンドウを残したままスイッチャー外で 100 回以上の他ウィンドウ／ダイアログの開閉を行った後でも、開いたまま残っている現在ウィンドウの 100% で保持されていたキャプチャ画像がアイコンへ戻らず維持される。
- **SC-002**: 保持上限（100 件）を超えるウィンドウ環境で新規キャプチャが発生した場合でも、直近アクティブ順上位のウィンドウ（最優先で切り替え対象となるウィンドウ群）のキャッシュ維持率が 100% に保たれ、古い未利用エントリのみが破棄される。
- **SC-003**: タイトル変化やサイズ変更、無名補助ウィンドウの併存が発生する複数ウィンドウ環境において、既存ウィンドウの識別紐付けが別 ID へ誤遷移または欠落する回数が 0 回である。
- **SC-004**: リスト型スイッチャー選択時および検索ランチャー利用時のキャッシュ保持件数 0 件・画面収録権限アクセス 0 回というプライバシー要件を 100% 維持する。

## Assumptions

- 本仕様は Issue #16 の確認で合意された「案 A（閉じられたウィンドウのキャッシュ自動整理＋LRU 順序逆転の修正＋上限 100 件化、およびウィンドウ識別照合の連続性強化）」に基づく。
- 縮小サムネイル 1 件あたりのメモリ消費量は約 0.45 MB（432×270 RGBA 相当）であり、上限 100 件かつ閉じ済みウィンドウの自動整理を併用することでメモリ使用量は約 45 MB 以下に抑えられ、ゼロレイテンシおよび省リソース方針と両立する。
- 新規に一度も画面表示されていない状態で再取得不能なウィンドウ（最小化中・別スペース等）や、画面収録権限が未許可のケースにおけるプレースホルダー（アプリアイコン）フォールバック仕様（`007-window-capture-switcher`）はそのまま維持される。
