## User Scenarios & Testing *(mandatory)*

### User Story 1 - 単一のバージョンファイルによる一元管理と自動タグ・リリース公開 (Priority: P1)

メンテナーは、リポジトリ直下のバージョンファイルにセマンティックバージョン（例: `0.1.0` や `0.2.0-beta.1`）を記述してメインブランチへ反映するだけで、手作業によるタグ作成やローカルビルド・アーカイブアップロードを行うことなく、該当バージョンのタグ作成、品質テスト、アプリパッケージのビルド、および配布用アーカイブを添付したリリースの公開までを自動で完了できる。

**Why this priority**: 手動のタグ打ち・ビルド・ZIP 圧縮・リリース添付によるヒューマンエラーやバージョン表記の食い違いを防ぎ、安全かつ再現性の高いリリース運用を確立することが本機能の最重要目的であるため。

**Independent Test**: バージョンファイルの値を新しいセマンティックバージョン（例: `0.1.0`）に更新してメインブランチへ反映すると、自動検証パイプラインが動作してテストをパスした後に `v0.1.0` タグが作成され、アプリ本体を内包した `Wintch-v0.1.0.zip` が添付されたリリースページが自動公開されることで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** バージョンファイルが有効なセマンティックバージョン（例: `0.1.0`）に更新され、そのバージョンのタグがまだ存在しない状態, **When** 更新がメインブランチに反映される, **Then** 自動テストが実行されて成功した後にタグ `v0.1.0` が自動作成され、アプリがビルドされて `Wintch-v0.1.0.zip` が生成・添付されたリリースが公開される。
2. **Given** バージョンファイルにプレリリース識別子を含むセマンティックバージョン（例: `0.2.0-beta.1`）が指定された状態, **When** 更新がメインブランチに反映される, **Then** タグ `v0.2.0-beta.1` が作成され、公開されるリリースが自動的にプレリリースとしてマークされ、`Wintch-v0.2.0-beta.1.zip` が添付される。
3. **Given** 既存のタグと重複するバージョン、またはセマンティックバージョニング規約に違反する文字列がバージョンファイルに記載された状態, **When** 更新がメインブランチに反映される, **Then** 新規タグの作成およびリリース公開は行われず、不正なバージョン指定または重複である旨のエラーが通知されて処理が停止する。
4. **Given** リリース用パッケージがローカルまたは自動パイプラインでビルドされた状態, **When** 配布用 ZIP アーカイブ `Wintch-v<バージョン>.zip` を展開する, **Then** ルート直下にアプリケーション本体（`Wintch.app`）が配置されており、Apple Silicon 環境および Intel 環境の双方で起動でき、アプリ内のバージョン表示もバージョンファイルの値と一致している。

### User Story 2 - 「Wintchについて」メニューからのアプリアイコン・バージョン確認 (Priority: P1)

ユーザーは、自分が現在使用している Wintch のバージョンが最新かどうかや問い合わせ時に伝えるべき版数を確認したいとき、メニューバーのアプリケーションメニューから「Wintchについて」を選択するだけで、アプリアイコンと現在のバージョン情報を専用ウィンドウですぐに確認できる。

**Why this priority**: 配布されたアプリをユーザーが利用するうえで、アプリ自身が正しいバージョンを提示できることはサポートやアップデート確認の基本要件であり、バージョン一元管理の成果をエンドユーザーが直接確認できる接点であるため。

**Independent Test**: ビルドされた Wintch アプリを起動してメニューバーアイコンをクリックし、「Wintchについて」メニューを選択すると、アプリアイコン・アプリ名・表示バージョン・ビルド番号・著作権表記を表示する専用ウィンドウが最前面に表示され、閉じる操作後も他の設定画面やウィンドウ切り替え機能が正常に動作し続けることで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** Wintch が起動してメニューバーに常駐している状態, **When** ユーザーがメニューバーアイコンをクリックしてメニューを開く, **Then** メニュー内に「Wintchについて」項目が表示されている。
2. **Given** メニューが表示されている状態, **When** ユーザーが「Wintchについて」を選択する, **Then** アプリアイコン、アプリ名「Wintch」、バージョン情報（表示バージョンおよびビルド番号）、および著作権表記を表示する「Wintchについて」ウィンドウが画面中央・最前面に表示される。
3. **Given** バージョン `0.1.0` としてビルドされたアプリで「Wintchについて」ウィンドウを開いた状態, **When** ユーザーがバージョン表示を確認する, **Then** 表示バージョンが `0.1.0` として正しく表示されている（ビルド番号が併記される場合も実際のビルド番号と一致している）。
4. **Given** 「Wintchについて」ウィンドウがすでに開かれている、または一度閉じた状態, **When** ユーザーが再度メニューから「Wintchについて」を選択する, **Then** 重複ウィンドウを作らずに既存の専用ウィンドウが最前面に再表示される。

### User Story 3 - 手動タグ作成によるリリースビルドの自動反映 (Priority: P2)

メンテナーは、ホットフィックスやリリース再生成などの理由で手動で `v*` 形式のタグを作成・プッシュした場合でも、バージョンファイル更新時と同じビルド・ZIP パッケージング・リリース成果物反映の仕組みをそのまま利用できる。

**Why this priority**: 自動タグ作成を基本運用としつつも、手動タグ作成や管理画面からのタグ付きリリース公開といった通常の Git リリース運用とも整合性を保つことで、運用上の柔軟性を確保するため。

**Independent Test**: リポジトリのバージョンと一致する新しいタグ（例: `v0.1.1`）を手動でリポジトリへプッシュすると、自動テスト・アプリビルド・`Wintch-v0.1.1.zip` の作成が実行され、該当タグのリリースページに成果物が反映されることで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** メンテナーが `v0.1.1` のタグを手動で作成してリポジトリへプッシュした状態, **When** 自動リリース処理が起動する, **Then** テストの成功後にユニバーサル形式のアプリがビルドされ、配布用アーカイブ `Wintch-v0.1.1.zip` が該当リリースに添付される。
2. **Given** すでに成果物付きのリリースが存在するタグに対して、リリース公開イベント等で再度ビルド処理が走った状態, **When** 成果物アップロードが行われる, **Then** 既存の同名アーカイブを上書き更新して重複エラーを起こさず、最新のビルド成果物が反映される。

---

### Edge Cases

- **バージョン以外の変更がメインブランチに反映された場合**: バージョンファイルに変更が含まれない通常のコード修正やドキュメント更新の反映では、自動タグ作成およびリリース公開は発動しない。
- **ビルド前の自動テストが失敗した場合**: ユニットテストが1件でも失敗した時点でパイプラインは中断し、タグの作成もリリース公開も行われない。
- **パッケージ化されていない開発時直接実行での「Wintchについて」表示**: アプリバンドルとしてパッケージ化されていない開発中の直接起動状態で「Wintchについて」を開いた場合でも、クラッシュせずフォールバックアイコンおよびフォールバックバージョン表示（または利用可能な情報）を安全に表示する。
- **バージョンファイルの前後空白・改行**: バージョンファイルの末尾に改行や前後の余分な空白が含まれていても、トリミングされた正しいセマンティックバージョンとして解釈される。
- **ビルド番号が取得できない環境でのローカルビルド**: Git 履歴が存在しないソースアーカイブ等でローカルビルドを行った場合でも、ビルド番号のフォールバック値（`1`）が設定されてビルドが失敗しない。
- **プレリリース版と通常版の判定**: `0.1.0-rc.1` のようにハイフン以降のプレリリース識別子が付与された場合はプレリリースとして扱われ、`0.1.0` のように `MAJOR.MINOR.PATCH` のみの場合は正式リリースとして扱われる。

## Requirements *(mandatory)*

### Functional Requirements

#### バージョン管理とビルド連携
- **FR-001**: プロジェクトルートに単一のバージョンファイル（`VERSION`）を配置し、セマンティックバージョニング（`MAJOR.MINOR.PATCH` および任意の `-<プレリリース識別子>`）形式でアプリのバージョンを一元管理しなければならない（MUST）。初期バージョンは `0.1.0` とする。
- **FR-002**: アプリケーションのパッケージ組み立て処理は、バージョンファイルから読み取ったバージョン文字列をアプリバンドルの公開バージョン情報（表示バージョン）へ自動反映しなければならない（MUST）。
- **FR-003**: アプリケーションのパッケージ組み立て処理は、アプリバンドルのビルド番号にリポジトリのコミット履歴数を自動設定し、コミット履歴を取得できない環境では `1` へフォールバックしなければならない（MUST）。
- **FR-004**: リリース用のアプリケーションパッケージ組み立て処理は、Apple Silicon および Intel の両環境で動作するユニバーサル実行形式のアプリバンドルを生成し、アドホック署名を付与しなければならない（MUST）。

#### 自動タグ作成とリリース成果物反映
- **FR-005**: メインブランチへの変更反映時にバージョンファイルが更新されていた場合、自動リリース基盤はバージョン値がセマンティックバージョニング形式に適合しているかを検証しなければならない（MUST）。不適合な形式の場合はタグ作成およびリリースを行わずに失敗として報告しなければならない（MUST）。
- **FR-006**: 検証を通過したバージョンについて、対応するタグ（`v<バージョン>`）がリポジトリにまだ存在しない場合、自動リリース基盤は品質検証のための自動テストを実行し、全テスト成功後にタグ `v<バージョン>` を自動作成・登録しなければならない（MUST）。
- **FR-007**: タグ `v<バージョン>` が作成された場合（自動タグ作成に連続する処理、または手動での `v*` タグの反映・リリース公開の双方を含む）、自動リリース基盤はリリース用ユニバーサルアプリをビルドし、アプリバンドルのディレクトリ構造を保持したまま `Wintch-v<バージョン>.zip` 形式の ZIP アーカイブを生成しなければならない（MUST）。
- **FR-008**: 自動リリース基盤は、該当タグに対するリリースページを作成（既存の場合は更新）し、生成した `Wintch-v<バージョン>.zip` をリリース成果物として添付し、自動生成リリースノートを付与しなければならない（MUST）。プレリリース識別子を含むバージョンではリリースを自動的にプレリリースとして設定しなければならない（MUST）。
- **FR-009**: 手動タグ作成またはリリース公開時のバージョンとバージョンファイルの値が一致しない場合は、バージョン不整合による不正な配布を防ぐため、エラーとして処理を停止しなければならない（MUST）。

#### 「Wintchについて」メニューと画面表示
- **FR-010**: メニューバー常駐メニュー内に「Wintchについて」項目を配置しなければならない（MUST）。
- **FR-011**: ユーザーが「Wintchについて」を選択したとき、他のメニュー操作やスイッチャー動作を阻害することなく、専用の「Wintchについて」ウィンドウを画面中央・最前面に表示しなければならない（MUST）。
- **FR-012**: 「Wintchについて」ウィンドウには、アプリアイコン、アプリ名「Wintch」、現在のバージョン（表示バージョンおよびビルド番号）、および著作権・ライセンス表記を表示しなければならない（MUST）。
- **FR-013**: 「Wintchについて」ウィンドウは複数回開かれても重複生成せず既存ウィンドウを再利用し、閉じた後でアプリ全体が終了しないようにしなければならない（MUST）。

### Key Entities

- **バージョン定義（Version Definition）**: プロジェクトルートで管理される単一のセマンティックバージョン値。`MAJOR.MINOR.PATCH`（例: `0.1.0`）および任意のプレリリース識別子（例: `-beta.1`）で構成され、タグ名（`v<バージョン>`）、配布アーカイブ名（`Wintch-v<バージョン>.zip`）、およびアプリ内の表示バージョンの唯一の信頼できる情報源（Single Source of Truth）となる。
- **リリース成果物（Release Artifact）**: リリース用にビルド・署名された `Wintch.app` を親ディレクトリ名ごと圧縮した配布用 ZIP ファイル（`Wintch-v<バージョン>.zip`）。
- **アプリ情報ウィンドウ（「Wintchについて」画面）**: ユーザーに向けて現在のアプリのアイデンティティ（アプリアイコン・アプリ名）、版数（表示バージョン・ビルド番号）、およびライセンス・著作権情報を提示する専用情報画面。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: バージョンファイルの更新から自動タグ作成・ユニバーサルビルド・`Wintch-v<バージョン>.zip` のリリース公開まで、メンテナーの手動介入ゼロ（1回のメインブランチ反映のみ）で 100% 自動完結する。
- **SC-002**: 配布用 ZIP アーカイブ `Wintch-v<バージョン>.zip` を展開した際、直下に `Wintch.app` が生成され、表示バージョン・ビルド番号・ZIP ファイル名・リリースタグ名の 4 箇所でバージョン表記の不整合が 0 件である。
- **SC-003**: セマンティックバージョニング規則に反する文字列や既存タグと重複するバージョンが設定された場合、誤ったタグ作成やリリース公開が発生する割合が 0% である。
- **SC-004**: ユーザーがメニューバーから「Wintchについて」を選択してから 0.5 秒以内にアプリアイコンとバージョン情報を視認でき、繰り返し開閉してもウィンドウの重複やアプリ終了が発生しない。

## Assumptions

- **コード署名方針**: 現時点のリリース配布では Apple Developer ID による公証（Notarization）は行わず、既存のローカルビルドと同じアドホック署名を継続する。将来的に Developer ID 署名・公証を導入する場合は本仕組みを拡張する。
- **初期リリースバージョン**: 既存のバンドル設定に記載されている `0.1.0` を本機能導入時の初期バージョンとする。
- **メニュー配置**: 「Wintchについて」はメニューバー常駐メニューの既存の「設定を開く...」付近に配置し、設定や終了操作と混同しない明確なラベルで提供する。
- **自動テストの前提**: リリース自動化パイプラインでは既存のユニットテストがすべてパスすることをリリース公開の前提条件とする。
